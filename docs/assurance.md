# What the checks establish

We want strong claims about native behavior. The current evidence is deliberately separated so that useful partial work does not masquerade as a completed proof.

| Evidence | Establishes | Does not establish |
| --- | --- | --- |
| Lean kernel checking | Imported theorem statements follow from their definitions and allowed axioms | That definitions match NNTP, HOL, the host, or hardware |
| `scripts/Audit.lean`, `leanchecker` and nanoda | Every declaration defined in a `lean/DN` module is re-checked by the Lean kernel and by an independent one, is not an axiom, `unsafe`, `partial`, `extern`, `export`, `implemented_by`, an initializer or a `csimp` theorem, and depends only on `propext`, `Classical.choice` and `Quot.sound`. The exception is the `_unsafe_rec` helper Lean generates to compile a recursive definition: it is `partial`, no checked declaration can use it, and neither kernel re-checks it | Nonvacuity, useful specifications, or runtime behavior |
| `DN.Dsl.Correct` | For every program of the source language that the emitter accepts, the lowered code, run in the model from a state where the input and output buffers are addressable and apart, writes exactly the program's reply and changes nothing else in memory; the exported function returns the reply's length, or refuses before writing anything. A closed instance on a concrete call in the model shows the premises can hold | That the model is the HOL semantics (item 1), that CakeML's parser reads the printed source as the lowering does (item 2), that the C caller receives the result whole (item 5), that CakeML's theorem covers the call (items 7 and 8), or that the language expresses NNTP |

The current audit covers 15,350 declarations, including 7,392 theorems and generated ones. It is a tripwire against unsound dependencies, not a measure of project completeness. Gate tests compile probe modules containing a foreign, private or top-level axiom, an axiom reached only through a constructor, `sorry`, `native_decide`, `implemented_by`, `extern`, `export`, `csimp`, initializers, `partial` (also a definition added directly as `partial`), `unsafe`, hand-written `_unsafe_rec` helpers, a failing, mistyped or non-executable regression, a declaration added without kernel checking, and a theorem that two modules store with different proofs, of which the import keeps one, and require each to be rejected.

nanoda (`ammkrn/nanoda_lib`), a Lean kernel written independently in Rust, checks every declaration of the library again, together with everything it uses from Lean's core library, from the export written by `lean4export`. Only unsafe and `partial` declarations are left out; the audit accepts none but Lean's `_unsafe_rec` helpers. nanoda admits `propext`, `Classical.choice` and `Quot.sound` and fails on any other axiom in the export, so a wrong proof would have to be accepted by both kernels. It recognizes the three axioms by their names written with dots and without escapes, so the export list is refused if any other axiom reads the same, such as `«Quot.sound»`. Gate tests require nanoda to reject a declaration added without kernel checking and foreign, private, `sorry` and `native_decide` axioms, and the export list to refuse such a lookalike and names that cannot be passed to `lean4export`. The export is read from the compiled `.olean` files, so the exporter and Lean's file loader remain trusted, as for `leanchecker`; the statements of the three axioms come from the pinned toolchain.

Because the build precedes these checks, the source gate (`scripts/SourceGate.lean`) runs first. It parses every module with Lean's own parser, in import order, and checks each command before Lean elaborates it. Commands, attributes, options and imports are allow-listed; syntax definitions are accepted only in files pinned by hash; `by_elab`, `run_tac`, `include_str`, `idbg`, tactic configuration values (compiled as unsafe code) and `unsafe` code are refused. Lean still evaluates library code in some places, for example for `decide +native`, but only as safe definitions, which cannot use unsafe primitives. The rules were reviewed for Lean 4.30.0, and a different `lean-toolchain` fails the gate until they are reviewed again. The audit re-checks every module's imports from its compiled header. `scripts/check.sh` refuses to start when git tracks build outputs, such as `.lake`, compiled `.olean` files, Lake traces or `.pyc` files, which Lake and Python would otherwise trust. It builds without Lake's shared artifact cache and fails if any repository file changes during the gate or the build.

The source gate is a tripwire, not an isolation boundary: building Lean code runs code, so a missed construct would run with the rights of the build, and untrusted changes must be built and checked in an isolated environment without secrets or network access. CI does so: the build job has no secrets, builds without network and cannot regain root, and the kernel re-checks and the audit's static checks run on a fresh machine from the build output before any built code is executed. These checks establish what the build produced; that the output corresponds to the sources still rests on the build running no code from the change. The checking scripts come from the change itself — for a pull request GitHub takes the workflow file, and everything it starts, from the pull request's own merge commit — so a green `checks` run says that those checks passed, not that the project's did. A second workflow (`.github/workflows/verify.yml`), which `workflow_run` always takes, file and checkout, from the default branch, publishes a check run saying whether every required job of that run succeeded and whether the files that decide what the checks do are the default branch's. Running the default branch's checks over the change instead would report an honest structural change as a failure, because the expected counts, the audited module list and the pinned syntax files move with the code they describe. So a change that edits its own checks is reported, not rejected, and the edit still needs review: the report is neutral, which a required check accepts, so it buys a visible, unforgeable statement rather than a block. A change that renames the `checks` workflow, or narrows its triggers, gets no report at all rather than a red one, because the run this reads would not exist; only a branch rule that requires the `verify` check turns a missing report into a blocked merge. CI status is advisory unless the repository requires it for merges.

The [inherited-code review](reviews/README.md) distinguishes fixed maintained-path defects from documented integration blockers. Corrected source comments now match these assurance boundaries.

## Open proof connections

1. **Semantics correspondence.** `DN.Compiler.Semantics` is a Lean transcription, not an automatically certified translation of the upstream HOL4 semantics. [The clause-by-clause comparison](pancake-semantics.md) records what it was compared against, by digest, and what it leaves out; a machine-checked bridge remains an obligation. The compiler's theorem asks that `semantics_decls` not fail, which first declares the program's functions and then runs `semantics`; `DN.Compiler.Entry` models the run from there. For a program of one `main` without parameters, as the server's are, the declaring step only puts the body where the call finds it; that is read off the HOL definitions, not modelled.

2. **Source representation.** The printed source is held against the tree the pinned parser builds from it (`scripts/parser_contract.py`). For every program `dn-compiler` prints — the kernels, the source-language example, the server's loop, the framers, the session's program, the gate's accepted examples and the differential fixtures, 224 in all, which together use every statement and expression form the gate accepts — `cake --pancake --explore` prints the tree its parser built, and that tree has to equal the lowered program once both are in one canonical form: chains of `+`, `*` and `&` nested to the right, statements as lists; the parser's program may hold no function besides them and the `main` the compiler adds.

   `DN.Compiler.Canon.canon_eval` proves that the canonical form identifies only expressions that evaluate alike, so the comparison cannot hide a difference. `DN.Compiler.Precedence.printed_well` proves, for every expression the gate accepts, that the printer leaves an operand without parentheses only where the table `reads` allows and prints every shift distance as a bare number; equations pin `ppExpr` to those decisions, so the theorem is about the printer as it stands. The contract holds each pinned parser to every one of that table's 320 cells, both ways; `printed_well` relies on 62 of them, and the rest record the grammar around them.

   What stays open is the theorem itself: for every function the gate accepts, the parser of each pinned revision (`pancake/parser/panPEGScript.sml` with `panPtreeConversionScript.sml`) turns its printed text into a program equal, in canonical form, to its lowering. It needs the parser's definition, which is CakeML's and lives in HOL4, not here; until then the correspondence is checked program by program and cell by cell. The source language's theorem ends at the lowered model program and rests on this as well. The differential suite exercises 35,520 arithmetic/control cases across Python, the Lean model, and native execution.

3. **Backend identity.** CI's native lanes use the release pinned in `tools.lock.json`. The curated datacake patch applies to the older source pinned in `backend/lock.json`. The patched HOL proof rebuild has been run here and the theorem it ends in carries no oracle. `scripts/bootstrap_cake.sh` builds an executable compiler from that patched source, outside CI (hours and tens of gigabytes), and the native lanes pass with it case for case as with the release ([backend](../backend/README.md#bootstrap-the-compiler)). No output we know of distinguishes the two compilers: the dead add-with-carry the patch removes is also removed later by the word language's dead-code pass. No theorem here covers the binary's behaviour, and upstream's end-to-end bootstrap theorem, which is not built, would not connect its Pancake mode to the compiler theorem either.

   The two pinned parsers are not the same: the release is the newer of the two, and its `Shift` takes the distance as an expression where the patched source's takes a number, so the release reads `(x) >>> 2 + c` as a shift by `2 + c` where the other refuses it. The parser contract runs against the release in CI and in `scripts/check_all.sh`, and against the bootstrapped compiler with `--bootstrapped`, which first checks its digest against `backend/bootstrap-record.json`; both read each of the 224 programs the compiler prints the same way.

4. **Shift distances.** The semantics gives a nonzero shift of a whole word or more no value, but the release compiler accepts `a >>> 64` and a variable distance without a diagnostic, folding or masking them. `Checked.emit` is what keeps the emitted subset inside the modelled behaviour: it takes only a literal distance below 64, for `>>>` and `<<` alike.

5. **Native ABI and memory.** The pinned export trampoline returns 32 bits to C; full-word results now use output slots via `Abi.wordResult`. See [the baseline findings](baseline.md). The C adapter, heap/stack sizing, generated machine code, and memory model need an explicit contract. The current adapter provisions 1 MiB each for heap and stack; these are tested allocations, not proven minima.

6. **Host refinement.** The Rust primitives and preserved OS reactors are not connected by a refinement theorem to the Lean dataplane models. FFI and kernel behavior are assumptions to articulate, not erase. The models state what they prove: a stale correlator stays rejected for the rest of a trace, a closed connection's token never resolves again, the deadline heap stays within twice its live content when it sweeps, a drain that clears its wakeup flag before reading its queue never drops a message silently — it either took it or will look again before sleeping — while two of the thirty-five schedules of the opposite order do drop one, and shedding from the middle of a byte stream is replaced by closing the connection. Each is a statement about the model, not about a running reactor.

7. **Entry points.** The Pancake compiler's correctness theorem (`pan_to_target_compile_semantics`) is stated for the `main` entry only. Every native lane here but the loop design of the entry benchmark, the server loop, the session and the NNTP server calls `export` functions from C after `cml_main` returns, a re-entry path the upstream theorem does not cover. Whichever way this is closed — a main loop that talks to the host through the FFI, or an extension of the upstream proof — no end-to-end statement holds before it is. The [decision](decisions/0002-entry-and-memory.md) is the main loop: the server runs inside `main` and fetches events in batches through external calls; the exported kernels stay as tests outside the theorem. The server's loop (`DN.Server.Skeleton`), a whole program built without `--main_return` that echoes payloads, and the NNTP session (`DN.Server.Session`) run that way, both proven in the model never to fail for any host (`DN.Server.SkeletonSafe`, `DN.Server.SessionSafe`), and the session's socket host (`native/nntp_host.c`) serves it from inside `main`: for the server, the entry is closed; what the host does between calls stays item 6's.

8. **Addresses the theorem admits.** The same theorem fixes the memory domain to the CakeML heap (`s.memaddrs = addresses base (heap_len - globals_size)`). A load or store through a pointer the C host owns — the result slot, the echo buffers, the control and output regions — is outside that domain, where the semantics gives `Error`, so the theorem's premise about the run not failing is false. Either those buffers live inside the heap the compiler knows about, or they are reached through the shared-memory operations that have their own domain, or the upstream proof is extended. The ABI adapter of item 5 states the caller's obligations; this is the one that decides whether the chain says anything at all. The [decision](decisions/0002-entry-and-memory.md) puts the buffers in the heap: the host fills and drains them only inside the external call that names them, and checks that every array it is given lies there; shared memory is kept for when a copy has to go, as with asynchronous completions. The theorem also fixes the first five words of the heap — the addresses of the compiled bitmaps and of the code buffer — which the start-up code CakeML emits writes for an ML program and not for a Pancake one. The hosts of the entry benchmark (`scripts/entry_bench.py`), of the server loop (`scripts/server_check.py`) and of the session's program (`scripts/session_native.py`, `scripts/nntp_check.py`) write them, through `native/cake_header.c`, and check them on the program's first external call, the server loop's and the session's hosts on every call; for every other run here the premise is false. The safety analysis that proves the server loop and the session never fail refuses any access to the heap's first 64 bytes: in the model, a run from a heap without those words never fails, so it never reaches them; that a run from the heap with them is the same run is the model's frame property, not proven. The server loop and the session keep every buffer in their heap, and their hosts check that each array handed over is exactly its area of the layout. One more premise stays open: CakeML's theorem allows a run to stop for want of stack unless the stack is at least a bound the compiler computes in HOL (`max_depth`), which it does not print; the host provisions 1 MiB, far more than the loop's frames were measured to reach, but the bound itself is not yet obtained.

9. **Protocol and persistence.** The first slice answers only what [decision 0003](decisions/0003-nntp-slice.md) fixes, against a store that is still empty; article storage, durable acceptance and crash recovery are not implemented. [Decision 0005](decisions/0005-article-store.md) fixes how they will be; its specifications are written, with what the rows above prove of them — which articles are accepted, the journal, the file system and its crashes, recovery, and the store's runs (`store_safe`), under the assumptions those rows state — while the program and the host that are to meet them are not yet written. How input is cut into lines and multi-line blocks — line boundaries, the octet limit, dot-stuffing — is specified over the whole stream and proven for the framers and for the functions printed from them (`DN.News.FrameSpec`, `DN.News.Framer`, `DN.News.FramerCode`); the session's `main` runs the line framer's statements in place, which is tested, not proven.

The inherited HTTP workloads, whose certificates rested on premises no state satisfies, were removed; `AssuranceChecks.lean` keeps the theorems that record why such universal bound-local and memory-domain premises are contradictory. `Certificate` requires an inhabited precondition. Fuel/clock bounds describe model execution, not elapsed CPU time.

## Reproducibility boundaries

The baseline pins Lean and Rust and uses locked Cargo dependencies. `tools.lock.json` pins by digest the elan, Lean, CakeML and lint tool archives and the sources of `lean4export`, nanoda and Poly/ML — the ML compiler the backend proof lane builds the prover with, so that a rebuilt proof names the compiler it rests on — and those of abnfgen, LazyFS with the two libraries its build would fetch, and libfiu, all of which are built outside the checkout so that its configuration files cannot take part; CI links the verified Lean release into elan instead of letting elan download it, and installs the Python linters from hash-pinned wheels. The bootstrap verifies stored archives on every use, and an installed tool against a manifest over its whole tree — every entry's kind, name, executable bit and content — so a tool changed or truncated after installation is refused instead of executed. The manifest is written beside the tool when it is installed rather than derived from the lock, so it establishes that the tool is still what was installed, not where it came from; use a fresh `.deps/tools` when artifact provenance matters. It is not a hermetic build of every system dependency.

CI uploads logs, emitted source, assembly, and a native report with hashes. Benchmark results vary with CPU, OS, compiler, and workload. A local region-digest measurement is a kernel microbenchmark and must not be reported as news-server throughput.
